This file is a continuation contract for another LLM working on this
repository. Treat `README.md` as the current operator-facing source of truth and
this file as the rationale, invariants, limitations, and handoff log from the
July 2026 staged implementation thread.

## Start here

1. Inspect `git status` and `git diff` before changing anything. Preserve all
   user and uncommitted work.
2. Read `README.md`, then inspect only implementation files directly relevant
   to the requested feature. Do not perform a broad repository rewrite.
3. Keep the existing small architecture: Node.js standard library, browser
   JavaScript/CSS, PowerShell, and the small C# launcher. Do not add a framework
   or runtime npm dependency without a concrete need and explicit approval.
4. Keep permissions on the server. A hidden or disabled UI control is never an
   authorization boundary.
5. Any new dashboard-to-agent action must be added deliberately to the server
   allowlist, validated there, handled narrowly by the agent, and covered by one
   focused protocol regression test.
6. Preserve the distinction between server-authoritative state and agent
   enforcement. The server owns sessions, class rules, message lifecycle,
   schedules, target expansion, and expiration timestamps. Agents report
   inventory/status and enforce commands.
7. Build artifacts in `dist/` are generated and ignored. Never assume
   `iD-Tech-Watch.exe` exists in a fresh checkout; run the documented build.
8. Use focused checks while implementing. Run the complete integration suite
   only at a final integration boundary.
9. Treat building access as server authorization. Never send instructor codes
   to an instructor browser or restore the former client-only comparison.

## Architectural invariants

- The hub is `server/server.js`; it serves the dashboard and owns both
  WebSocket endpoints.
- The director role is named `admin` in code and persisted state. Do not rename
  it casually because that is a shared auth/protocol value.
- Organization hierarchy is Location → Building → Class. Physical agent
  location/building comes from enrollment; class assignment remains
  server-managed.
- Persistent hub state is JSON at `data/config.json` unless
  `IDT_CONFIG_PATH` overrides it.
- Browser sessions are random 48-character hexadecimal tokens held in memory
  for 12 hours.
- Instructor WebSocket sessions begin with no authorized buildings. A
  successful `building_auth` exchange adds one building to that connection;
  reconnecting intentionally requires the code again.
- Newly created buildings receive a random four-digit code. Legacy buildings
  missing a valid code are migrated on load; do not restore a predictable
  default.
- Instructor state is filtered: building codes are redacted, device inventory
  and layouts are limited to unlocked buildings, and schedules are
  director-only.
- Remote commands use structured actions and parameters, never shell command
  strings. `DASHBOARD_COMMANDS` is the external command boundary.
- DOM helpers assign untrusted content as text. Do not reintroduce HTML string
  interpolation for device names, application labels, messages, or org names.
- Temporary blocks/messages become absolute `expires_at` values on the server
  so reconnects do not reset durations or make individual agents authoritative
  for classroom lifecycle.
- Detected application choices are suggestions from current agent inventory.
  Persisted class rules store normalized exact executable identifiers.
  Manually entered identifiers remain supported when the app is not currently
  open.
- Focused-window closure has a request ID and an explicit result protocol. Do
  not report dispatch acknowledgment as successful closure.

## Packaged client and process lifecycle

The downloadable artifact is exactly:

```text
dist\iD-Tech-Watch.exe
```

Build it with:

```powershell
powershell -File scripts/build-agent-exe.ps1
```

The build uses the Windows .NET Framework C# compiler and embeds:

- `agent/agent.js`
- `scripts/agent-watchdog.ps1`

At runtime, `launcher/iD-Tech-Watch.cs` resolves the active user's actual
Documents known folder and uses:

```text
Documents\iD-Tech-Watch\
```

This decision avoids repository-relative or administrator-profile paths when a
student launches the downloaded file. The launcher refreshes embedded runtime
files, saves setup in `config.json`, clears a previous authorized-shutdown
flag, and starts one hidden watchdog. The watchdog passes configuration through
environment variables rather than constructing a command from user-controlled
strings; this reduces command-line injection and quoting risk.

If the agent exits unexpectedly, the watchdog waits two seconds and starts it
again. The supported intentional stop is:

```powershell
iD-Tech-Watch.exe --shutdown
```

That writes `shutdown.flag` before stopping the PID-recorded Node and PowerShell
processes. The flag is intentionally retained so the watchdog cannot interpret
the stop as a crash. Normal launcher startup removes the flag.

Do not replace this with broad process-name killing. PID files are paired with
an expected process-name check to reduce the chance of terminating an unrelated
process.

## Authenticated download decision

The browser cannot use a plain anchor because the application stores its
session token in local storage and the server requires a Bearer header. The
bottom-right control is therefore a real button that:

1. fetches `/download/id-tech-watch.exe` with the active token,
2. surfaces a useful server error,
3. creates a short-lived object URL, and
4. downloads with the fixed name `iD-Tech-Watch.exe`.

The server accepts only `GET`, validates instructor/admin role, uses a
server-controlled path, returns a portable-executable content type and
Content-Disposition, disables caching, and excludes `/download` variants from
the single-page-app fallback. `IDT_AGENT_EXE_PATH` exists for server operation
and isolated tests; it is not request-controlled.

## Major staged changes and why

### Location and application discovery

- Location sign-in gained fuzzy matching and keyboard autocomplete, including
  Tab completion. This keeps the existing hierarchy while making multi-campus
  lookup tolerant of human input.
- Open applications became structured inventory rather than relying only on
  window titles. Display labels remain presentation data; executable identity
  is the enforcement key.

### Message lifecycle

- Warning and transition messages became server-authoritative and survive
  reconnects. Agents request/receive current message state instead of assuming
  a disconnect clears instructor intent.
- Informational messages remain ordinary one-way notices.
- Optional message durations are represented as absolute expiration times.
  A legacy scheduled-message value of `timeout_sec: 0` is migrated to “no
  timeout” by removing the field, because zero is not a valid positive
  duration.

### Blocking lifecycle

- Application and website blocks accept optional validated durations and use
  absolute expiration.
- Class application rules persist in class configuration and sync to connected
  agents on assignment/reconnect.
- Rule creation supports detected inventory and explicit manual executable
  identifiers. Server normalization and duplicate checks prevent fuzzy labels
  from becoming unsafe enforcement patterns.

### Focused-window closure

- “Close focused window” is a distinct action from killing a named process or
  closing every browser.
- The hub tracks a request ID, correlates the agent response to the target
  device, times out unanswered requests, and reports success/no foreground/
  unsupported/timed out/failed to the instructor.

### Final packaging and security

- Added the authenticated instructor/director client download.
- Added a C# setup/bootstrap executable, Documents runtime layout, watchdog,
  and authorized no-restart shutdown.
- Made the launcher request elevation before starting production monitoring so
  hosts-file and process enforcement do not silently run without permission.
- Added a server command allowlist so a valid dashboard session cannot invent
  arbitrary agent actions.
- Replaced the former browser-only building-code check and deep-link bypass
  with a server-verified `building_auth` protocol. Commands, class rules,
  layouts, state visibility, and reconnect behavior share that boundary.
- Added normalized command targets/parameters, bounded agent status and
  registration text, one-megabyte WebSocket payload limits, and deterministic
  duplicate-device connection replacement.
- Updated `scripts/run_server.ps1` to require Node 22 and build the downloadable
  client automatically when missing.
- Added a focused download security/integration regression test.
- Rewrote `README.md` to document the current system rather than the original
  prototype.

## Known limitations and next-project risks

- The executable is unsigned and Windows may show a reputation warning.
- Node.js is still required on student computers; the EXE embeds application
  source and lifecycle tooling, not the Node runtime.
- Client setup and an optional enrollment token are stored as local JSON, not
  Windows Credential Manager secrets.
- The watchdog restarts the agent, but it is not itself installed as a Windows
  service. A user who forcibly terminates the watchdog can defeat restart until
  the launcher runs again. Managed deployment should move this lifecycle to a
  signed Windows service or MDM policy.
- Hub sessions are memory-only and disappear on restart.
- Hub config uses one JSON file and is not safe for multi-process writes or
  large multi-site scale.
- The default director password is `changeme` unless overridden. Production
  setup must set `IDT_ADMIN_PASSWORD` and configure instructor access.
- Transport is plain HTTP/WebSocket by default. Use TLS termination and `wss`
  outside a trusted LAN.
- Agent enrollment uses an optional shared token, not per-device certificates.
- Application/site enforcement relies on Windows process and hosts-file
  mechanisms; browser DoH, portable applications, permissions, and endpoint
  security policy can affect enforcement.
- Instructor building authorization is connection-scoped by design. A
  reconnect requires the four-digit building code again instead of persisting
  that secret in browser storage.
- The legacy scheduled-task installer remains for direct-development use and
  is separate from the downloaded launcher lifecycle. Do not mix both startup
  mechanisms on the same computer without deliberately reconciling them.
